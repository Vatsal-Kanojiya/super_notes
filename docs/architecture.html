1. What it is

Super Notes keeps your notes in sync across your devices. It also has "Ask your notes". You type a question. The app finds the relevant parts of your notes and has an AI model answer from them. The answer carries citations. Each citation links back to the note it came from.

Notes are stored as TipTap documents (JSON). A background worker cuts each note into chunks and turns each chunk into a vector. Search mixes keyword search and vector search, and always filters by owner in SQL.

3. The provider layering

Embeddings and chat both use the same four-layer shape. The rest of the app never sees a vendor.

flowchart TB app["App code
indexer, search, ask task"] --> boundary boundary["Boundary function
embed_texts / embed_query | complete
plain args in, plain result out, checked"] --> registry registry["Registry
name to import-path string
chosen by EMBEDDING_PROVIDER / CHAT_PROVIDER
imported lazily"] --> adapters adapters["Adapters
fake | openai | gemini | claude (chat only)"] --> vendor["Vendor HTTP API"]
  • Boundary. retrieval/embeddings/__init__.py and assistant/chat/__init__.py. They normalise input and output. The embedding boundary refuses blank text, batches calls, and checks every vector is finite and the right size. The chat boundary returns a plain ChatResult. No vendor type or HTTP detail crosses it.
  • Errors. Two kinds. A permanent error means give up. A transient error (429, 5xx, timeout) means Celery retries with backoff.
  • Registry. A dict of names to dotted path strings, resolved with import_string only when chosen. A broken adapter cannot stop the others loading. An unknown name raises the permanent error.
  • Adapters. fake is the default. It needs no network or key, so tests and local runs work. Real adapters use plain requests. API keys come from environment variables, never from app settings.
  • Stored model id. Each vector is saved with the embedding model id, so the indexer knows when a stored vector belongs to an old model.
Add a vendor: write one adapter file in providers/ that implements the base protocol, then add one line to that registry's dict. Set EMBEDDING_PROVIDER or CHAT_PROVIDER to its name, add its model name to the models setting, and put its key in the environment.

4. Workflows

4a. Sign in with Google, refresh, logout

Endpoints: auth/google/, auth/refresh/, auth/logout/. Any sign-in failure returns one generic error, so nothing leaks about why.

sequenceDiagram autonumber participant C as Client participant A as API participant G as Google certs participant DB as Postgres C->>A: POST auth/google/ (ID token) A->>G: verify signature, expiry Note over A: audience is in our client-id list
iss is accounts.google.com
email_verified is true A->>DB: find user by Google sub, then by email alt none found A->>DB: create user end A->>DB: register device (refresh token chain) Note over A,DB: limit is 2. A third sign-in signs the oldest out
(blacklist its refresh token, log event) A-->>C: access + refresh JWT, profile C->>A: POST auth/refresh/ (refresh token) A->>DB: blacklist old refresh, issue new pair, update device row A-->>C: new pair (old refresh is now dead) C->>A: POST auth/logout/ (refresh token) A->>DB: blacklist token, drop device row A-->>C: 204, this device is signed out

Access tokens last 30 minutes by default. Refresh tokens last 14 days and rotate on every use. A device signed out by the limit can still use its current access token until it expires, but it cannot refresh.

4b. Edit a note

sequenceDiagram autonumber participant C as Client participant A as API (notes/services.py) participant DB as Postgres participant Q as Redis / Celery C->>A: PATCH notes/id (changes + version) A->>DB: begin transaction, lock the owner's User row A->>DB: revision = notes_revision + 1 A->>DB: re-read the note alt version differs A-->>C: 409 with the server copy (rolled back, no revision gap) else version matches A->>DB: version + 1, revision = new, save (content_text derived) A->>Q: on_commit: index_note_task(note, version), countdown 20 s A-->>C: 200 updated note end

The owner-row lock makes revisions come out in commit order. The version check happens after the lock, so two saves with the same version cannot both win. The indexing task is enqueued only after commit, so a worker never looks for a row that is not visible and a rolled-back write is never indexed. Deletes make a tombstone and enqueue with no delay.

4c. Sync between devices

sequenceDiagram autonumber participant C as Device participant A as API participant DB as Postgres C->>A: GET notes/changes/?after=rev A->>DB: read the ceiling first (User.notes_revision) A->>DB: notes with rev less than or equal to ceiling and greater than after, ordered by revision, limit+1 A-->>C: results (live notes and tombstones), latest_revision, has_more Note over C: store latest_revision, repeat while has_more is true

Reading the ceiling first is the trick. Everything at or below it is already committed, so the list is complete. A note written twice appears once, at its newest revision. A deleted note arrives as a tombstone so the device can remove it.

4d. Indexing a note

in progress The chunker and embedding providers are built. The indexer and task are being built now.

sequenceDiagram autonumber participant W as Celery worker participant DB as Postgres participant E as Embedding provider W->>DB: load note alt note deleted W->>DB: delete its chunks (de-index) else version is not the requested one Note over W: stop, a newer task will handle it else Note over W: chunk the TipTap tree by headings and list items
hash each chunk's embed text W->>DB: fetch stored vectors (same model id) by content hash W->>E: embed only the chunks with a new hash (no lock held) E-->>W: vectors W->>DB: lock note row, re-check version alt version changed while embedding Note over W: write nothing else same W->>DB: atomic swap: update, create, delete chunks end end

Chunks target about 1600 characters with a little overlap, and never cross a heading. The embedded text starts with the title and heading path, so "move it to Friday" still knows its note. The job is safe to run twice. Permanent errors are logged and dropped. Transient errors retry with backoff.

4e. Ask your notes

planned The endpoint, model, task and quota are not built. The prompt, citation parsing and chat providers are.

sequenceDiagram autonumber participant C as Client participant A as API participant DB as Postgres participant T as Celery task participant P as Chat provider C->>A: POST ask/ (question, Idempotency-Key) A->>DB: lock user, check quota A->>DB: create AskQuery (pending) A-->>C: 202 + query id A->>T: enqueue T->>DB: hybrid retrieval: vector + full-text, merged with RRF, owner filter in SQL alt nothing clears the relevance floor T->>DB: store "couldn't find anything" (no LLM call) else T->>T: number excerpts, build prompt with delimited excerpts T->>P: complete(system, user) P-->>T: answer text with [n] markers T->>T: parse [n] to citations, drop invented numbers T->>DB: store answer, citations, token counts end loop poll C->>A: GET ask/id A-->>C: status (and answer + citations when done) end Note over C: render answer, make [n] clickable to the cited note
  • A repeated Idempotency-Key returns the existing query instead of charging quota twice.
  • Quotas default to 20 (free) and 500 (premium) asks. The exact window is decided with the model.
  • Note text is data. The prompt wraps excerpts in tags and escapes any tag a note tries to close, to blunt prompt injection.
  • The stored answer is kept verbatim. Only citations that match a real excerpt become links.

6. Data model

The user field names shown are the intent. Check accounts/models.py for exact columns. The AskQuery fields are a sketch. The model is not built. version answers "did this note change since I loaded it". revision answers "what changed since I last synced".

7. Run locally

Needs Postgres 16 with pgvector, Redis, Python 3.x and Node. Full setup is in README.md.

python manage.py migrate                 # also enables pgvector
python manage.py runserver               # API at :8000, docs at /api/v1/docs/
celery -A config worker -l info          # background indexing (and ask, later)
cd web && npm install && npm run dev     # Vite dev server, usually :5173
# set CORS_ALLOWED_ORIGINS=http://localhost:5173 and VITE_API_BASE_URL in env
python manage.py test                    # the suite

Where the docs live, all in docs/: COMMIT_PLAN.md (phases and status), CONVENTIONS.md (rules carried from the expense tracker), DECISIONS.md (each choice and why), RAG.md (chunking, embeddings, and later ask and eval), BUILD_LOG.md, BACKLOG.md. The API contract is at /api/v1/schema/.
