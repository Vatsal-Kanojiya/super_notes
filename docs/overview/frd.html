01Accounts and security

Purpose

Sign in with Google only, keep each account's data private to its owner, and let people see and end their own sessions.

Functional requirements

IDRequirementDecision
FR-AUTH-01Sign in with a Google ID token (signature, audience, expiry, issuer, verified email); every refusal is the same google_failed.D6, D14
FR-AUTH-02An email already tied to a different Google account is refused.D13
FR-AUTH-03Access token lasts 30 minutes, refresh token 14 days; refresh rotates and blacklists the old token.D19, D20
FR-AUTH-04At most 2 devices signed in; a third sign-in signs out the least recently used one.D6, D17
FR-AUTH-05A user can list devices and sign one out; logout ends the current device.D17, D18
FR-AUTH-06Profile (name, email, plan, usage, limits) readable at me/; timezone and memory switch editable.D15, D84
FR-AUTH-07New accounts stop for the day once the daily signup limit (30) is used; existing accounts still sign in.D91
FR-AUTH-08Security events (sign-in, logout, memory cleared, push subscribed) are kept 365 days, never with content.D16

  A-->>B: Access 30 min + refresh 14 d

  A-->>B: 401 when expired
  B->>A: POST auth/refresh

Endpoints

POST/api/v1/auth/google/POST/api/v1/auth/refresh/POST/api/v1/auth/logout/GET/api/v1/auth/devices/DELETE/api/v1/auth/devices/{id}/GET/api/v1/me/PATCH/api/v1/me/

Rules and limits

30 minaccess token
14 daysrefresh token
2signed-in devices
30 / daynew accounts (system)
365 dayssecurity event retention
30 / hoursign-in throttle

Edge cases handled

  • Replayed refresh token: 401, because the old one is blacklisted at once.
  • Concurrent refresh locks the old token row, so only one wins.
  • A signed-out device's access token lives out its 30 minutes (accepted, D19).
  • Signups closed: 403 signups_closed, existing users unaffected.
  • Anonymous callers are throttled at 60 / hour, by the proxy-aware client address.

Functional requirements

  • Google ID token verified: signature, audience, expiry, issuer, verified email.
  • Rotating refresh tokens, blacklist on use, device cap of 2.
  • Deny by default: every view needs auth unless named public.
  • Owner filter in every SQL query; foreign ids are 404.
  • Uploads: magic bytes, size caps counted in-stream, random names, nosniff, no public URL.
  • Prompt injection: excerpts are delimited data; memory never reads excerpts; format guardrail.
  • Scoped throttles: sign-in 30/h, search 120/h, ask 60/h, format 30/h, summary 30/h, upload 120/h.
  • Security events kept 365 days, without content.

Performance

  • pgvector HNSW index on 1,536 dimensions, ef_search 200, 50 candidates a leg.
  • Index work debounced 20 s; embeddings in batches of 64.
  • Caps: 1 MB note, 12,000 excerpt characters, 24,000 format and summary input, 100,000 file text.
  • Answers run in a worker; the API returns 202 at once.
  • Hashed assets cached for a year.

Reliability

  • Idempotency-Key on ask, turns, format and summary creation.
  • Reminder delivery is at most once (unique claim row).
  • Refunds on failed or stuck jobs; sweepers every 5 minutes.
  • Celery soft and hard time limits; provider read timeout 60 s.
  • Stream falls back to polling; search falls back to keyword.
  • Version conflicts return 409 with the server copy.

Privacy

  • Every row is owner-scoped; no sharing in V2.
  • Email carries title, date and link only, never the note body.
  • Push carries only an id to open.
  • Memory is visible, deletable, switchable off; forget-all in one call.
  • Security events and usage never hold note content or file names.
  • Files served only to their owner, as attachments.
