1. In one minute

supermemory

A memory and context layer for AI apps. You send it text, chats and files. It keeps document chunks for search, and it also extracts short facts about a user and keeps them up to date. You ask it for the user's profile or for relevant facts, and paste the result into your prompt.

For: developers building a chatbot or agent that should remember users.

codebase-memory-mcp

A code index for AI coding agents such as Claude Code. It parses your source into a graph of functions, classes and calls, stores it in SQLite, and lets the agent query it over MCP. The agent asks "who calls X?" instead of running grep and reading files.

For: people who use coding agents, especially on large repos.

The key difference. supermemory remembers what users said and prefer, to make an app's answers personal. codebase-memory-mcp remembers how your code is wired, to make a coding agent's searches cheaper. They do not compete. Only the first is relevant to the Super Notes product; the second is a developer tool.

2. supermemory explained

Repo: supermemoryai/supermemory. MIT licence. A TypeScript monorepo (Next.js web app, docs, an MCP server, SDK wrappers, a memory-graph UI component). The README calls it "the memory and context layer for AI".

The flow

Memories vs chunks

A chunk is a piece of the original document, found by similarity. It is the same for every user. A memory is a short fact the system extracted: "Alex works at Stripe as a PM". It belongs to a user or entity and changes over time. Supermemory keeps both and searches both. You already do chunks in Super Notes. Memories are the new part.

Fact extraction and how memories change

An LLM reads new content and writes atomic facts. Each new fact is linked to old ones by one of three relations (the type is updates | extends | derives in the repo's packages/validation/schemas.ts):

Day 1   "Alex works at Google as an engineer"   isLatest = true
Day 40  "Alex just started at Stripe as a PM"   UPDATES Day 1
                                                Day 1 -> isLatest = false  (kept for history)
"Alex is a PM"  EXTENDS the Stripe fact         "Alex likely manages roadmaps"  DERIVES (isInference)

Contradictions: the newer fact supersedes the older one; search returns only the latest by default. Forgetting: a fact can carry forgetAfter (for example "exam tomorrow") and a forgetReason, and it drops out after that date. The schema fields I confirmed in the repo: version, isLatest, parentMemoryId, rootMemoryId, isStatic, isInference, isForgotten, forgetAfter, memoryEmbedding.

Static vs dynamic profile

profile.static  = ["Senior engineer at Acme", "Prefers dark mode", "Uses Vim"]     stable, long-lived
profile.dynamic = ["Working on auth migration", "Debugging rate limits"]           recent, changes often

The profile is one call that needs no query. The idea: you attach it to every prompt so the model always knows who it is talking to, instead of hoping a search finds it. The docs claim ~50ms (a claim, not measured here).

Container tags

A containerTag is a string such as user_123 that you pass on every add, search and profile call. The docs call it a "hard isolation boundary" (user, tenant or project). Scoped API keys can be restricted to one tag. This is the multi-user model: you choose the tag, and supermemory keeps tags apart. Metadata filters work inside a tag.

Search modes and connectors

  • Hybrid search (default searchMode: "hybrid") returns document chunks and memories in one query. "memories" returns facts only. Docs say the engine has vector, full-text and graph built in.
  • Connectors: Google Drive, Gmail, Notion, OneDrive, GitHub, web crawler (plus S3 and Granola docs pages) sync content in.
  • File processing: PDFs, images (OCR), video (transcription), code.

How you would use it

# Python SDK (from the README)
client.add(content="User loves TypeScript", container_tag="user_123")
r = client.profile(container_tag="user_123", q="programming style")
r.profile.static   # long-term facts
r.profile.dynamic  # recent context

Other routes: framework wrappers (Vercel AI SDK, LangChain, OpenAI Agents, Mastra, ...) and an MCP server at https://mcp.supermemory.ai/mcp with three tools: memory (save or forget), recall (search plus profile), context (inject the profile). Plugins exist for Claude Code, Cursor, Codex and others. Note the MCP and plugins are for your own AI assistant remembering you. They are a different use than putting memory inside an app for its users.

Hosted vs self-hosted, and what the licence covers

Finding. The repo's LICENSE is MIT, but the memory engine is not in it. What I found in the clone: the Next.js web app (apps/web has only a landing page and config), the docs, the MCP server, SDK and framework wrappers (packages/tools, Python SDKs), a graph-visualisation component, a Raycast extension, and type/validation schemas. I found no code for fact extraction, the graph engine, embeddings pipeline, or the supermemory-server binary. The docs say the extraction is done by "a custom learning model and a graph database that we built internally".

So MIT applies to what is in this repo: the client side. The self-hosted "Supermemory local" binary is described in the docs as "free, open source", with a link to git.new/memory. I did not follow that link, so I cannot say where its source lives or under what licence. Treat "self-hostable" as true (docs describe a single binary that runs offline with Ollama) but "open source engine under MIT" as unverified.

3. codebase-memory-mcp explained

Repo: DeusData/codebase-memory-mcp. MIT licence. Written in C, shipped as one native binary. It has no LLM inside. Your coding agent is the "query translator": it decides which graph tool to call.

The pipeline

Node and edge types

Nodes (README, "Graph Data Model"): Project, Package, Folder, File, Module, Class, Function, Method, Interface, Enum, Type, Route, Resource (Docker and Kubernetes objects).

Edges: containment (CONTAINS_PACKAGE/FOLDER/FILE, DEFINES, DEFINES_METHOD, MEMBER_OF), code relations (IMPORTS, CALLS, CALL_REFERENCE, USAGE, IMPLEMENTS, USES_TYPE, WRITES), web and config (HTTP_CALLS, ASYNC_CALLS, HANDLES, CONFIGURES, REFERENCES_FILE), and others (TESTS, FILE_CHANGES_WITH). Some extra edge kinds (DATA_FLOWS, SIMILAR_TO, EMITS) appear in the feature list.

Parsing is tree-sitter for 162 languages (claim), with a lighter type-resolution layer for about 10 of them including Python, TypeScript and Go. For Django code the call graph will be best-effort: dynamic Python (signals, getattr, ORM magic) cannot be fully resolved statically.

What installing it changes on your machine

The README is direct about this: "This tool reads your codebase and writes to your agent configuration files." Running install auto-detects coding agents and, for each one found, writes:

  • The MCP entry (for Claude Code, ~/.claude.json).
  • Instructions and skills (for example AGENTS.md pointers, a skill file) and three sub-agent definitions (Scout, Verify, Auditor) where the client supports them.
  • Hooks in Claude Code: SessionStart, SubagentStart, a non-blocking PreToolUse on Grep/Glob/Bash (it nudges the agent to use the graph), and a post-Read coverage check.
  • A binary on your PATH and a background daemon shared across sessions (watcher, optional UI on a local port). Logs go under ~/.cache/codebase-memory-mcp/logs.

Options: --skip-config installs the binary only. Manual setup is one JSON entry in ~/.claude.json or a project .mcp.json. codebase-memory-mcp uninstall removes what it owns. Installation via curl ... | bash runs a script from the internet; the README says releases are checksummed and scanned, which I did not verify.

Claims to treat as claims. "120x fewer tokens" (five queries: ~3,400 vs ~412,000 tokens), "10x fewer tokens, 83% answer quality" (from an arXiv preprint written by the project), Linux-kernel index in 3 minutes, "8,050 tests". Not reproduced here. The repo does include docs/MEASURING_SAVINGS.md for testing on your own workload.

Pattern: the retrieval half is done, and is arguably more controlled than supermemory's. The missing half is all about memory over time, which is exactly the backlog's top V2 item.

Why not replace retrieval with supermemory

  • Control. You built chunking, RRF and the eval harness so you can see why a note was or was not found and measure it. supermemory's chunking and ranking are inside a service you cannot tune the same way, and its benchmarks are not on your notes.
  • Owner isolation in SQL. Today a user's rows cannot be read by another because the query itself filters on owner. With supermemory, isolation is a containerTag string your code must always pass correctly. It is a fair model, but it moves a guarantee from your database to a service's API.
  • An extra service, and maybe a licence gap. You would run or pay for a second system, keep it in sync with Postgres (every note edit, delete and account deletion), and depend on an engine whose source I could not find in the MIT repo. Notes are private data: the hosted API means sending them to a third party.

The in-stack V2 idea: UserFact

Copy the useful idea (facts that supersede each other) and keep it inside Django and Postgres. Sketch:

UserFact
  user          FK, owner isolation as everywhere else
  text          "Prefers answers in bullet points"
  kind          static | dynamic
  source_ask    FK to the Ask that produced it
  valid_until   null, or a date (dynamic facts expire)
  superseded_by FK to UserFact, null (see below; or use valid_until only)
  embedding     vector, same provider boundary as chunks
  • Supersede, do not delete. On a contradiction, set valid_until on the old fact and insert the new one. History stays for debugging. Retrieval filters valid_until IS NULL OR valid_until > now().
  • Same pipeline, new table. Facts use the same embedding boundary and the same hybrid or vector query with an owner filter in SQL. Your eval harness can get a second fixture set: "does the right fact surface?".
  • Risks to plan for: the extractor inventing facts (keep the source ask, let the user see and delete facts); private facts leaking into answers the user did not expect (show them in the UI); cost (one extra small LLM call per ask; use the cheap model); and a bad fact poisoning later answers (cap how many are injected).
  • Start small: static facts only, top 5 by similarity, no dynamic expiry. Add the rest if the eval shows it helps. Multi-turn chat is the feature that really needs this, so build them together.

codebase-memory-mcp as an optional dev tool

It is unrelated to the product. The question is only whether it helps you when you work on the Super Notes code with a coding agent.

  • Honest benefit: small. Super Notes is a modest Django codebase. Agents already handle it with grep and a few file reads, and docs like RAG.md and BUILD_LOG.md give them a map. The big claims (10x to 120x fewer tokens) come from large repos and from the project itself. You might see faster "who calls this?" and "what does this change affect?" answers (trace_path, detect_changes). You would not see a dramatic saving.
  • Python and Django limits: signals, Celery task dispatch by name, DRF routing and ORM calls are dynamic, so some edges will be missing or guessed. An agent may trust a graph answer that is incomplete. The tool's own docs say a clean coverage check means only "no recorded gap".
  • Risks: it writes to agent config and installs hooks that change how your agent searches; it runs a background daemon; the installer is a piped shell script; it is a young project by a small team with fast-moving changes (a single huge mcp.c of ~12k lines, visible in the clone). Your working tree has uncommitted work from another agent, so any tool that hooks into agent behaviour should be tried in a separate clone.
  • Cheap way to try: install --skip-config or a manual .mcp.json entry in a throwaway copy of the repo, index it, ask five real questions, compare with plain grep. Uninstall if it does not help.

6. Verdict and next steps

  • supermemory: do not adopt, do borrow the idea. Your retrieval is already the stronger, more controllable half. The part you lack (facts, profile, supersede, expire) is small enough to build in Postgres.
  • Read, do not install, for design: the supermemory docs pages "Graph memory" and "User profiles", and the memory schema in packages/validation/schemas.ts, are a good checklist for a UserFact design.
  • Plan UserFact together with multi-turn chat. Both are the V2 "conversation memory" goal. Build static facts first, extraction in Celery, top-k into the Ask prompt, and add an eval fixture so you can measure it like retrieval.
  • codebase-memory-mcp: optional, low priority. Try it in a throwaway clone for an afternoon if you want. Expect a small gain on this repo. Do not let it touch your main setup until you have read the hooks it would add.
  • If you ever reconsider supermemory, first find where the self-hosted engine's source and licence really live, and decide whether notes may leave your servers.
